# Feature Engineering — Google Play Sentiment Pipeline

## Overview

This document describes the feature engineering layer built on top of the
cleaned review data. Features are generated by `feature_engineering.py`,
stored in the `features` table in the database, and exported to
`features.csv` (local only) and `features_sample.csv` (available in repo).

The goal is to produce an analysis-ready feature dataset that supports
future EDA and sentiment modeling work, rather than optimizing model
performance at this stage.

---

## Feature Table Schema

| Field | Type | Description |
|-------|------|-------------|
| review_id | VARCHAR | Primary key, linked to cleaned_review |
| app_name | VARCHAR | Name of the app being reviewed |
| app_category | VARCHAR | Industry category of the app |
| review_length | INT | Character count of the cleaned review text |
| rating_group | VARCHAR | Grouped rating: positive (4-5), neutral (3), negative (1-2) |
| review_date | DATE | Date the review was posted |
| review_weekday | VARCHAR | Day of the week the review was posted |
| review_month | INT | Month the review was posted (1-12) |
| has_reply | BOOLEAN | Whether the developer replied to the review |
| is_low_signal | BOOLEAN | True if review is under 20 characters |
| is_duplicate | BOOLEAN | True if review content is identical to another review |
| is_english | BOOLEAN | True if review is predominantly ASCII characters |
| service_signal | BOOLEAN | Contains service-related keywords |
| login_signal | BOOLEAN | Contains login or account-related keywords |
| price_signal | BOOLEAN | Contains price or payment-related keywords |
| refund_signal | BOOLEAN | Contains refund or billing-related keywords |
| update_signal | BOOLEAN | Contains update or version-related keywords |
| positive_signal | BOOLEAN | Contains strongly positive sentiment keywords |
| negative_signal | BOOLEAN | Contains strongly negative sentiment keywords |
| feature_generated_at | TIMESTAMP | Timestamp when features were generated |

## Feature Descriptions

### Structural Features

**review_length**
Character count of the cleaned review text. Longer reviews tend to
contain more specific feedback and higher sentiment signal value.
Short reviews (under 20 characters) are already captured by is_low_signal.

**rating_group**
Star ratings grouped into three categories:
- positive: 4 or 5 stars
- neutral: 3 stars
- negative: 1 or 2 stars

Grouping reduces noise from individual rating differences and provides
a cleaner label for downstream classification tasks.

**review_date / review_weekday / review_month**
Temporal features derived from the review timestamp. Useful for
identifying seasonal patterns, update-driven sentiment changes,
or day-of-week posting behavior differences across app categories.

**has_reply**
Whether the developer posted a reply to the review. Apps with high
reply rates (e.g. TikTok at 84%) may reflect stronger customer
engagement strategies. Useful for comparing service quality across apps.

---

### Quality Features

**is_low_signal**
Carried over from the quality_flag layer. Reviews under 20 characters
typically lack sufficient context for meaningful sentiment analysis.

**is_duplicate**
Carried over from the quality_flag layer. Duplicate content may indicate
coordinated review campaigns or template submissions.

**is_english**
Carried over from cleaned_review. Non-English reviews may require
separate handling in downstream NLP tasks.

---

### Topic Signals

Topic signals indicate whether a review discusses a specific issue area.
They are derived from simple keyword matching and should be treated as
approximate indicators rather than precise classifiers.

Keywords were selected based on frequency analysis across 20,731 reviews.
The top 5 signals by occurrence rate were chosen.

| Signal | Keywords | Occurrence Rate | Negative Rate |
|--------|----------|----------------|---------------|
| service_signal | support, help, response, contact, customer service | 6.0% | 45.5% |
| login_signal | login, account, password, sign in, access | 5.0% | 72.8% |
| price_signal | price, expensive, free, premium, worth | 4.9% | 45.1% |
| refund_signal | refund, charge, billing, subscription, cancel | 3.1% | 75.5% |
| update_signal | update, version, broke, after update, new version | 3.0% | 54.1% |

**Negative Rate** refers to the proportion of reviews containing that
signal that have a 1-star rating. login_signal and refund_signal show
the strongest negative correlation, making them reliable indicators
of user pain points.

---

### Sentiment Signals

Sentiment signals use strongly polarized keywords to approximate the
emotional tone of a review independent of its star rating.

| Signal | Keywords | Occurrence Rate | Alignment with Rating |
|--------|----------|----------------|----------------------|
| positive_signal | love, amazing, perfect, excellent, great | 14.1% | 82.7% in 4-5 star |
| negative_signal | terrible, awful, worst, horrible, useless | 2.9% | 86.7% in 1-2 star |

Alignment rate refers to the proportion of reviews containing the signal
that also have a corresponding high or low star rating. Both signals show
strong alignment, confirming their value as weak sentiment proxies.

---

## Limitations

**Keyword matching does not account for context.**
Negation ("not great"), sarcasm ("great, another crash"), and comparative
sentences ("used to be amazing, now terrible") can cause misclassification.
Signals should be used alongside rating_group rather than as standalone
sentiment labels.

**Topic signals are approximate.**
A review containing "cancel" may refer to cancelling a subscription
(negative intent) or successfully cancelling an unwanted charge (neutral
or positive). The signal captures the topic, not the sentiment direction.

**Temporal coverage is limited.**
All reviews in the current dataset fall within a single month (June-July
2026). Seasonal or long-term trend analysis is not yet possible with
this dataset.

**Features are regenerated in full on each run.**
The features table is truncated and rebuilt each time
`feature_engineering.py` is executed. This is appropriate for the
current stage but may need incremental update logic as the dataset grows.
